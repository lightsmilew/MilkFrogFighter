# 启动性能与资源调度

## 2026-10-21 Pages 请求链、缓存与资源清理

本轮先用空浏览器访问实际 Pages。该次本机网络约 1.48 秒就绪，没有资源错误；这不能代表用户的网络速度。记录显示启动前有 23 个请求，其中 15 个 JavaScript 文件分约三轮发现。线上响应缓存为 `max-age=600`，原资源使用固定文件名，跨部署的资源复用缺少保障。两张高场景此前已经不阻塞开打，不能把慢启动全部归因于它们。

生产构建现在使用 esbuild 合并并压缩脚本，启动只请求一个游戏模块；CSS 同时压缩。代码、图片、图标和原声按文件内容生成 URL，未变化的素材跨部署保持同一地址。Service Worker 只缓存使用过的资源，不提前下载所有角色、地图或音频，不缓存 HTML；页面从网络更新到新的资源哈希，最多保留 96 个缓存条目，存储不可用时正常走网络。首次加载完成后在空闲时间补存已请求的文件，不阻塞开打。

开局只优先下载两位默认角色。头像、主页装饰、地图缩略图和当前全景在开打就绪后请求。加载失败或超过 10 秒时提供手动重试，避免一直停留在不明确的等待提示。

原始记录：`artifacts/startup-pages-before.json` 与 `artifacts/startup-after.json`。本地服务器无 gzip，不能直接拿这些限速数据与实际线上 1.48 秒比较。实际页面还会受地区到 GitHub Pages 的链路、设备和浏览器存储回收影响。

`test:delivery` 将生产包挂在 `/MilkFrogFighter/`，用真实服务器统计外部请求，并模拟一份代码变化、素材不变的新部署。检查重新访问时复用图像、CSS 与旧脚本，新部署获取新脚本且不重下原图；另检查存储受限仍可开始对战、脚本失败后的手动重试。报告保存在 `artifacts/delivery-report-*.json`。测试中的命中时间不代表线上导航耗时。

Chromium 测试会清空 HTTP 缓存；WebKit 使用持久浏览器配置，测试服务器对所有资源返回 `no-cache`。两者均确认原图和样式没有再次到达外部服务器。WebKit 还验证失败脚本重试使用新请求地址，避免复用先前的失败记录。引擎测试不等同于 Safari / 夸克真机验证；无痕模式和系统清理存储时不能保证保留资源。

`assets/` 已删除 5 份废弃 WebP 和 2 张被高场景替代的 PNG，共 7337409 字节。仍用于离线处理的 6 张原图（12677478 字节）移到 `art/source/`，相关脚本和文档已更新。构建使用明确的运行素材清单，并拒绝 `assets/` 中未使用的文件；发布包不会包含原图。目录中有文件不代表浏览器自动下载它，下载由页面引用和加载代码决定。

## 专属跑步与图集合并

八帧行走、六帧新绘跑步与战斗动作合入每位角色唯一的一张 35 帧图集；旧的两张行走和一张疾跑被替换，六个独立 walk 文件删除，不再产生独立 run 文件。图集按非空矩形排列，虚拟帧从 256 缩至 192，显示尺寸与物理身高保持原值；一套动作解码后的帧画布从 32×256² 降到 35×192² 像素，新增跑步后仍减少约 38.5%。

`assets/` 从 24 个文件 / 2382008 字节降至 18 个 / 2017536 字节，减少 364472 字节（15.3%）。六位角色的动作 WebP 总量由 1525058 字节降至 1158400 字节，减少约 24%；元数据增加，用于存储裁边后的源矩形与还原位置。缩略图保留用于未加载角色的首页选角，可避免为了展示头像下载六份完整图集。

同一限速条件下，合并版首开 3448 ms、传输 596418 字节、最长任务 87 ms，与合并前接近。主要收益是总资源量、后续动作请求和解码占用下降；首开仍为一个游戏模块和开局两张角色图集，未增加独立跑步请求。当前原始报告为 `artifacts/startup-after.json`、`artifacts/running-assets-report.json`。Chromium / WebKit 再次通过仓库子路径、资源复用、代码变化的新部署和受限存储回退。

## 前一轮的离线图集优化

测试日期：2026-10-20。本机 Edge Chromium，禁用缓存，网络延迟 120 ms、下载 200000 字节 / 秒（约 1.6 Mbps），CPU 降速 4 倍。统计从导航到开打按钮可用，属于同机模拟条件，实际手机和线上网络仍会不同。

优化前单次记录：约 14.25 秒可开打，完成下载约 2.25 MB，最长主线程任务 2457 ms。原因包括开打等待两张全景、老街图和两张动作图全部下载；在浏览器中进行连通分量处理及六份逐像素染色；选图直接引用完整地图；HTML 还预加载了一张不再需要的大背景。

优化后同条件记录约 3.8–4.3 秒可开打，关键路径资源约 0.66–0.75 MB，最长主线程任务约 100–130 ms。报告和精确条件保存在 `artifacts/startup-after.json`，修改前记录为 `artifacts/startup-before.json`；运行 `tests/startup.browser.mjs` 可重新测量。

实际修改：

- 移除旧大背景预加载，优先请求开局两位选手图集，提前发现主要模块。
- `scripts/prepare-assets.py` 离线提取轮廓、校准锚点与配色；运行时直接读已打包的 24 帧 WebP，无逐像素处理。
- 未选角色使用小型正式头像图；完整角色图集选择后才加载，开始对战会保证双方动作就绪。
- 2026-10-21 重绘为两张 1254×1254 的高背景，完整天空、街道和前景覆盖 3840 单位高度，运行 WebP 为 286778 / 284200 字节。替换此前 1983×793 的矮全景，源 PNG 不进入部署包。
- 选图使用 12412 / 11596 字节的缩略图；全景只加载当前选择的一张，不阻塞开打。具体生成与映射见 `stage-prompts.md`。
- 大背景失败时使用已有画面回退。浏览器检查主动阻止两张大地图请求，仍能开始对战。
- 打包排除源 PNG、旧未引用图集、文档和测试。日常构建使用现成 WebP，无 Python 依赖。

完整浏览器回归同时检查资源错误、六位新角色素材、地图与触屏；性能检查还断言大地图和旧图集不出现在开打前的请求路径。
